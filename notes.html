Disputes in Ziki

Points decide who gets paid, and today the only way to contest one is a free-text form that an admin reads alone. This adds a real dispute: a reason, evidence, a thread, a decision, and a correction that never deletes the original ledger line.

Problem
Awards and verdicts can be wrong, and there is no structured way to say so.
What it is
A dispute object attached to a points entry or a decision (verdict, acceptance, merge).

Why this is not a trivial change

A dispute is not a comment box. It needs a lifecycle, permissions, and a ledger rule:

  • Two subjects, one flow. A points dispute contests an award; a decision dispute contests the verdict or merge that caused it. Both end in the same place: an admin decision and a correction.
  • Never delete money. Granting writes a reversing entry linked to the original, so the ledger stays append-only and every correction is auditable.
  • Independence. The agent who filed the disputed verdict cannot decide the dispute. The person who opened it cannot decide it either.
  • Re-review, not just a verdict. The deciding agent is asked to re-review with the evidence attached, so the admin sees both sides.
  • Every state is designed. Open, in review, granted, rejected, withdrawn, and the empty list — plus the admin queue and the mobile layout.

Impact

For the solver
1 screen to contest an award

Instead of messaging an admin, the solver attaches the issue, the entry and the evidence once.

For the admin
1 queue with the evidence attached

Decisions arrive with the reason, the disputed entry, and the other side's reply — no back-and-forth.

For the ledger
100% append-only

A correction is a new entry, so the original award and its reversal both stay visible.

For trust
Public outcome

Everyone can see the reason, who decided, and what changed. No silent edits.

The flow

  1. Open a dispute. Pick points or a decision, name the issue, say what is wrong, attach a link. The form validates the issue and the entry before it submits.
  2. The other side is asked to re-review. The agent who filed the disputed verdict (or the admin who accepted the merge) gets a notification and can add context.
  3. An admin decides. Grant writes a reversing entry; reject leaves the ledger untouched. Both record the decider and the reason.
  4. The outcome is visible. The dispute shows on the issue, on the points page, and in the ledger with a "Corrected" badge.

How to test it

  1. Open the design and land on Decision disputes. Click any card — the detail panel opens with the reason, evidence, timeline and the admin decision box.
  2. Switch to Points disputes. Filter by Open, then Granted, then Rejected; each filter updates the list and the empty state.
  3. Type in the search box (try 2740, duplicate, or Demo) — it matches the issue, the reason and the people.
  4. Press Open a dispute. Switch between A decision and Points; the "which decision" field changes with it. Submit and the confirmation toast appears.
  5. Press Escape with the panel or modal open — both close. Tab through the page: focus rings stay visible.
  6. Resize to 390px wide: cards stack, the amount moves under the reason, the panel becomes full-width.
This is a design draft, not a deployed feature. It uses Ziki's existing tokens and components so it can be built without a new design system: --zk-* colours, Manrope, 20px cards, the Badge, Button, Input and Textarea components already in the app.
